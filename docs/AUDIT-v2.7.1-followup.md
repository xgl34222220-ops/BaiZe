# 白泽 v2.7.1 后续可靠性审查

基线：main `702d81e91c83938f52a77c37a9d4112e8ca5e881`。问题：用户反馈升级后仍持续显示“连接中”。

本次沿 Root 启动与绑定、界面状态、任务互斥、配置/历史、白名单、文件归类、媒体刷新、安装发布链路检查关键边界。它是代码审查和自动化验证，不是所有 ROM 的真机兼容认证；没有用户设备日志，不能断言已经复现其唯一根因。

## 已实施

## 必须继续处理的风险

1. **P1：文件归类“目标不存在”与 rename 之间存在竞争窗口。** `FileOrganizerEngine.moveVerified` 和跨文件系统复制均先检查 exists 再调用可覆盖目标的 Os.rename。其他应用同时创建同名文件时，检查不足以保证不覆盖。应使用支持“不覆盖”的文件系统操作并补并发创建目标的设备测试；回滚路径同样需要验证。不能用更多 exists 检查代替原子保证。
2. **P1：共享统计与配置的读改写缺少统一事务。** `SchedulerRepository.saveConfig`、`WhitelistRepository`、`HistoryRepository` 的多步更新可能互相覆盖；`cache-lane-worker.sh` 会把任务侧 totals.env 整体回写全局，等待锁目录消失并不等于持有写锁。本次唯一临时文件只保证单次文件替换完整，不能防止逻辑更新丢失。下一步应统一跨进程锁/单写入者，并按任务 ID 汇总增量、保证重复完成不重复计数。
3. **P2：安装状态依据上次记录的 bundle hash。** 用户另行安装 APK 后，saved_hash 不能证明当前已安装内容就是模块内置版本。应比较实际安装包版本及签名后区分“更新可用、外部更新、签名冲突”；本次先修正失败诊断和自动降级行为。
4. **P2：授权被拒后再授予，libsu core 缓存可能仍认为无 Root。** 当前明确提示重启 App；下一步应通过公共 Shell API 完整设计重新授权流程，并覆盖拒绝→授予测试，避免反射修改内部状态或关闭其他任务共用的 Shell。
5. **P2：同步 Binder 调用仍可能受服务侧阻塞影响。** 已移走已发现的启动媒体 I/O，但需真机 StrictMode/耗时记录继续检查注册进度回调、绑定已有 daemon 的路径。30 秒启动期限只解决新进程无回调，不承诺中断已阻塞的同步 Binder 调用。

## 已检查、应保留的行为

- 清理的任务互斥、取消标记、快照指纹、白名单和危险路径限制有实际用途，不能按“过度防御”整体删除。
- `TaskCoordinator` 进程内互斥与进度节流应保留；跨进程任务一致性需单独加强。
- 历史读取虽然使用 readLines，但写入路径通常保留最近 100 行；目前更优先解决并发统计，而不是为此新增数据库。
- 归类已有指纹复验、同名冲突处理、跨文件系统复制校验和撤销记录；它们不能替代上面的原子不覆盖保证。
- 媒体队列以持久 pending/inflight 文件和回调确认防止丢刷新，不能为了启动快直接丢弃积压队列。
- 正式发布工作流检查版本一致、固定签名证书和校验和；不回退 Debug 签名。源码维护的 libsu bootstrap 依赖现有保留规则，不能随意删除反射入口。
- App manifest 目前无 INTERNET 权限；连接诊断存在应用私有目录，清理路径和日志不自动发送给外部服务。

## 发布验证

- 本地：新增安装器行为测试与 git diff --check 已通过。
- PR Android CI：编译、JVM/Robolectric 测试、lint、预览 APK；最终结果以 PR 检查为准。
- Core CI：shell 语法和完整回归套件；最终结果以 PR 检查为准。
- 真机尚待：Android 16/用户 ROM 冷启动、拒绝授权、授权后重启、30 秒无回调、手动重连、切后台再返回、主/缓存服务单独失败、后台清理期间重开 App。
- 归类与统计的 P1 项尚未解决，不能把本次结果描述为“全面无风险”。

## 捐赠功能的准备顺序

1. 先稳定连接、归类不覆盖和统计一致性；确保用户可以自行查看版本、更新记录和复制诊断。
2. 在“关于”页提供自愿支持入口，说明用于维护、兼容测试和功能开发。清理、错误修复和数据恢复入口保持可用，不把错误提示变成捐赠弹窗。
3. 收款渠道和收款信息确定后再实现跳转/二维码。优先由外部支付应用完成，不让 Root 服务参与支付，不提前增加账户系统或常驻支付 SDK。
4. 不读取支付应用私有数据来判定是否捐赠；不伪造“已到账”状态。若未来需要订单或回执，应以所选渠道实际支持的能力设计。
5. 致谢名单仅收录明确同意公开的昵称；版本、开源许可、联系方式和捐赠说明保持清晰可查。
