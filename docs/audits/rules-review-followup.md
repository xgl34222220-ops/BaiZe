# 2.9.1 规则与缓存执行链复查

## 发现与修复

| 实际问题 | 旧行为证据 | 本次行为 |
|---|---|---|
| 外部缓存扫描成功但无法删除 | `cache_path_matches_package()` 先匹配 `/data`，导致其子目录 `/data/media/...` 永远按内部路径解析并被拒绝 | 优先匹配媒体根；用户 0/10 的外部缓存均通过真实 scan→clean 回归 |
| 单个大文件屏蔽整个应用缓存 | `snapshot_cache_rec()` 设置目录级 `oversized`，临时清单整体不提交 | 仅跳过超过大小上限的文件，单独计入保护数量/字节，其余文件仍可清理 |
| 自动缓存保留期互相覆盖 | shell 对内部、外部天数取较小值后传给同一参数 | 原生新增独立外部保留期；内部 7 天、外部 0 天各自生效；手动扫描两者仍不受后台保留期限制 |
| 通配深度规则的显式风险不生效 | 规则 `*/cache|critical` 被存成含星号的祖先路径，无法匹配展开后的真实目标 | 先展开再绑定显式风险，内置与用户覆盖都采用同一逻辑 |
| 宽泛父规则吞掉受保护子规则 | 父目录为 low 时先整体进入快照，子路径标为 critical 仍可能被包含 | 有超出当前风险上限的显式子保护时，父目录不能整体进入删除计划；其他明确的可清理子目标仍独立处理 |
| 扫描后改风险策略，旧快照仍能删 | 深度消费脚本只复核规则库与白名单 | 同时复核扫描时记录的内置/用户风险覆盖哈希及配置哈希，变化要求重新扫描 |
| 隐藏垃圾与下载保护自相矛盾 | `.xlDownload` 同时被标为 critical，又在隐藏垃圾中以 0 天清理 | 从隐藏垃圾规则移除，保留下载内容；中断下载由原有带保留期的专用规则处理 |
| 隐藏 `.nomedia` 绕过白名单 | 隐藏目录处理后直接 `rm -f .nomedia` | 移除旁路删除；规则文件收集保护媒体、占位与锁标记 |
| 正好满 1 天的文件还要再等近一天 | `find -mtime +1` 实际要求达到 2 天 | 原生按秒比较截止时间；兼容路径使用等价的 `-mtime +(N-1)`；文件规则也按秒校验 |
| 慢目录无限扫描或部分结果伪装完成 | 规则目录 `find` 无执行上限，缓存报告把截断字段写死 0 | 原生目录收集 15 秒预算、外层 18 秒终止；部分清单不进入删除；失败计入错误/保护，缓存慢目录与截断标记保留到 App 读取状态 |
| 路径校验漏掉起始 `../` | `safe_relative_tail()` 只检查中间与结尾穿越段 | 按每个分段校验，拒绝起始/中间/结尾穿越、空段与非法规则控制字符 |

## 规则覆盖与执行效率

- 规则库实际校验为应用 299 条、外部 159 条、隐藏 21 条、深度 4,714 条、风险覆盖 232 条；无拒绝项、无重复项，深度规则哈希与元数据一致。
- 新的 `rule-targets` 原生命令一次解析应用/外部规则，按包名排序查找，只枚举设备上存在的包目录，输出 NUL 分隔目标；保留符号链接与越界校验。原有 Shell 发现路径作为缺少原生 ABI 时的回退。
- `collect-rule-files` 用目录文件描述符与 `fstatat` 遍历，一次得到普通文件和空文件清单；不跟随目录内符号链接、不跨文件系统、不收集白名单子树。原先规则目录的两次文件树遍历合并为一次，空目录在实际删除后另行检查，保证结果正确。
- WebView 从固定单进程 `app_webview` 扩展到 `app_webview*`、`app_hws_webview*`、`app_x5webview*`，内部和设备保护用户目录均支持。仅匹配明确的 HTTP/GPU/代码缓存及已完成崩溃报告，不删除 Cookies、IndexedDB、Local Storage 或整个 WebView 数据目录。
- 根清理器与深度直接清理结束后使共享索引过期，避免旧 TTL 状态再次显示刚删掉的文件。
- 相关原生/深度/快照入口识别全部实际清理 worker，避免把其他模块的活动锁误当过期锁。

## 验证

新增 `v2/tests/test-rule-engine-followup.py` 用实际引擎与 Shell 调用验证：

1. 默认嵌套存储根下的外部缓存能真正删除；混合大文件、白名单文件和扫描后变更文件保留。
2. 内部、外部自动保留期分别生效。
3. 文件年龄、最大尺寸边界、空文件、标记文件、目录符号链接、白名单与停止行为。
4. 多用户/设备保护/外部规则发现，规则路径穿越与越界拒绝。
5. 原生与 Shell 回退的真实 `rules-clean` 均删除预期日志与多进程 WebView 缓存，保留下载暂存、媒体标记与 Cookies。
6. 通配风险、父子保护、穿越规则拒绝，以及深度扫描后的内置/用户风险和配置变更使快照失效。
7. 空目录发现输出部分清单后返回 124/1 时，丢弃清单、保留全部空目录并报告不完整；返回 9 时传播停止，不继续删除。

旧深度恢复回归要求：父目录因大文件受保护后，明确的低/中风险子规则仍可被处理；高/critical 子规则保持既有保护行为。审查中曾尝试在预展开阶段去重，发现该行为被破坏后已撤回；继续由已有不可变快照构建器在成功遍历父目录后去重。该保护恢复测试已通过。

验证包含既有原生风险/上限测试、兼容清理功能测试、深度清理与恢复测试、规则元数据检查。所有耗时数据均来自宿主测试；本次没有连接用户真机，不作实际手机提速倍数承诺。

## 参考与边界

参考 SD Maid 官方对 [AppCleaner](https://github.com/d4rken-org/sdmaid-se/wiki/AppCleaner) 的“可重建文件”定义，以及 [SystemCleaner](https://github.com/d4rken-org/sdmaid/wiki/SystemCleaner) 的元数据过滤边界：本次采用明确应用归属、可重建缓存、逐项保护与可解释结果，不机械复制或增加广泛用户数据删除规则。

清理速度仍受文件数量、存储状态、厂商权限与应用持续写入影响。已改变或不可确认的文件继续跳过；对配置哈希发生变化的深度快照，哪怕只是修改定时配置，也会要求重新扫描，避免旧删除计划沿用旧风险策略。当前原生规则目标发现覆盖 Android 内部/设备保护和 `/data/media/<user>/Android/data`；并未把可移动盘应用私有目录泛化为自动删除范围。
