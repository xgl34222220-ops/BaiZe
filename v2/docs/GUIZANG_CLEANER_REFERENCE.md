# 归藏参考与白泽缓存清理优化

日期：2026-09-26。交付基线：正式版 2.0.0 之后的 `main`，提交 `2fe7af869b9ead4385e7f68a8fbfc45849b85623`，App/模块版本代码均为 `30005`。该基线包含正式标签 `refactor-v2.0.0` 的模块目录调整和结果展示修正。

上一轮 PR #217/#218 错用仍为 1.1.1 / 30004 的 v7 测试分支；`BaiZe-PR217-Test1.apk` 和配套模块已作废。这里重新从正式版基线迁入清理优化，保留 2.0.0 的 UI、模块结构和在线更新信息，并在构建中校验实际 APK、源模块信息和 ZIP 内模块信息均为 2.0.0 / 30005。

## 参考包里能确认什么

用户提供 `归藏-v0.1.0-alpha1(2).zip`，SHA-256 为 `c42537c0b1ce46cabd3d8729605a9b6a01b327104962f88dffcecf9a8e985451`。

- `payload/guizang-cleanup` 是静态链接、已去符号的 ARM64 ELF，SHA-256 为 `f5afe8b2acc244d604e5e6818c3d86507af4b8209d2e1a96afefdd5cdd56de90`。包中没有这部分 Rust 源码。
- 二进制字符串包含 `src/purge.rs`、`jwalk-0.8.1`、`rayon-1.12.0`、`rayon-core-1.13.0`、`crossbeam-channel`、`aho-corasick` 和 `purge-rayon-`。这些是并行遍历/线程池/规则匹配组件的证据，不能据此还原所有执行路径或给出真机速度比。
- `payload/guizang.toml` 将“清理前刷新规则”设为 false，支持缓存规则与独立定时。
- APK 反编译调用点 `oh2.java` 通过 `/api/purge/run` 发送 `kind`，读取 `bytes/files/ms/errs`。调用返回或动画完成不等于所有存储维护工作量可直接对比。
- 页缓存回收、FITRIM、F2FS GC 与删除应用垃圾文件属于不同操作，不能把它们的数字混为“释放存储”。

本次借鉴有限并行、减少重复目录工作、复用规则判定的思路；没有复制或运行归藏载荷，也没有改动温控、进程管理等功能。

## 白泽已有能力与本次改动

2.0.0 已有 2–4 工作线程扫描应用缓存，普通规则/空项目/碎片使用单次共享存储遍历，并用扫描快照直接清理。它并不是每次都用 shell 逐文件操作。

本次针对 App 前台缓存链路：

1. 按实际存在的用户和应用目录发现缓存，消除“包名集合 × 所有用户 × 所有缓存位置”的无效探测。
2. 在进入 WebView 子树前去除 owner CE 别名，避免 `/data/data` 与 `/data/user/0` 重复扫描。保留 legacy 路径回退。
3. 使用固定编译的路径规则，避免每个缓存根为同一个包重复编译五条正则。只对有结果的应用加载名称。
4. 同时处理最多 2–4 个应用；同一应用的缓存目录顺序执行。工作队列只提交有限数量的应用组，结果由调用线程合并。
5. 停止后不再启动剩余目录，等待正在执行的任务返回，并计入它们已完成的删除。未开始的目录完整保留；部分完成目录扣除已删除计数并标记未完整统计。
6. 修复白名单应用仍进入 WebView 发现，以及 `app_webview/Cache` 等已发现缓存被清理路径校验拒绝的问题。
7. 删除前复核缓存根的真实路径，拒绝扫描后父目录被替换为符号链接的目标。只删除缓存根内容，保留缓存根；继续跳过子树符号链接。

本次未改动后台自动化模块、安装包策略、高风险规则、UI 或版本号。

## 主机文件树对比

同一进程交替测试旧版与新版，共 4 轮，每个版本每轮新建相同布局：32 个应用、6 个用户目录、96 个缓存根、768 个子目录、12,288 个文件，每文件 256 字节，总计 3,145,728 字节。缓存包括普通缓存、代码缓存与 `app_webview/Default/Cache`。用 `System.nanoTime` 计算墙钟时间。

这组既有基准直接取 v7 提交 `cfcca719abf341c36cc226327e16d79f1f3f123f` 的缓存引擎源码。该文件与本轮 2.0.0 基线中的 `ForegroundCacheEngine.kt` 字节一致。测试仅重命名类并把 `/data` 路径重定位到临时目录；算法保持原样。每轮核对候选、字节数、文件数和实际删除结果，缓存根保留。旧/新删除均为真实宿主文件系统删除。

| 四轮中位数 | 既有缓存引擎（v7 / 2.0.0 相同） | 本次改动 | 耗时降低 |
| --- | ---: | ---: | ---: |
| 扫描 | 49.683 ms | 44.509 ms | 10.4% |
| 删除 | 214.007 ms | 75.002 ms | 65.0% |

原始数据见 [cache-fastpath-host.csv](benchmarks/cache-fastpath-host.csv)。

这是 Linux 主机 + Robolectric 的合成负载，不是归藏与白泽的真机对比，也不是 HyperOS/一加速度承诺。单个应用占绝大多数缓存、慢速闪存、后台应用持续写入等情况下收益会不同。尚需用相同的真实缓存数据，在 K80 至尊版与一加15上分别确认扫描、删除、停止与重试耗时。
